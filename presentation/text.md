# Слайд 1. Проект в 30 секунд

Это Telegram-бот для игры в Blackjack, который поддерживает два режима: одиночную игру в личном чате и групповую игру в общем чате. С пользовательской точки зрения сценарий довольно простой: открыть single-раунд, создать групповое лобби, присоединиться к нему, запустить раунд и делать игровые действия через команды или кнопки. Но с инженерной точки зрения это не просто чат-бот, а распределенная система, в которой нужно гарантировать корректный порядок событий, устойчивость к дублям, консистентность таймеров и целостность игрового состояния.

Я сразу проектировал систему не как набор handler-ов вокруг Telegram API, а как event-driven backend с явными границами ответственности. Это позволило отделить транспорт, orchestration и доменную логику, а также сделать систему расширяемой: например, поддержка split, insurance, таймаутов, админских операций и групповой семантики добавлялась без слома базовой архитектуры.

# Слайд 2. Общая схема

Сквозной поток выглядит так: Telegram Bot API отдает update в poller через long polling, poller публикует нормализованный envelope в Kafka topic, orchestrator читает этот поток, преобразует update в доменную команду, вызывает game service по HTTP и затем отправляет пользователю ответ обратно в Telegram. Отдельно Redis используется как fast state layer для дедупликации, session context и таймеров, а PostgreSQL отвечает за персистентное состояние игры и транзакционную запись side effects.

Микросервисная архитектура здесь выбрана не ради модного лейбла. Если попытаться решить эту задачу монолитом, то очень быстро смешиваются несколько принципиально разных типов ответственности: polling Telegram, разбор входных сообщений, пользовательский UX, таймеры, игровой state machine, persistence и админские сценарии. В таком варианте concurrency и error handling начинают протекать через весь код. Я разделил систему на сервисы по оси change rate и по оси failure domain. Poller отвечает только за ingest updates. Orchestrator отвечает за маршрутизацию, user-facing guards, дедуп и таймерную механику. Game service отвечает только за доменную модель blackjack и транзакционное обновление состояния. За счет этого каждый сервис можно масштабировать и тестировать в своей плоскости.

Взаимодействие между сервисами сделано асинхронным на участке ingest и синхронным на участке принятия доменного решения. Между poller и orchestrator стоит Kafka-совместимый брокер, потому что это естественная граница между внешним нестабильным API Telegram и внутренней бизнес-логикой. А между orchestrator и game service выбран HTTP, потому что здесь нужен request-response контракт: оркестратор делает конкретную команду и сразу получает актуальный snapshot игры для рендера ответа.

# Слайд 3. Poller

Poller решает одну задачу: безопасно и предсказуемо забирать updates из Telegram и доставлять их в Kafka. Я использовал long polling, а не webhook. Для MVP и учебного production-like проекта это более управляемая модель: не нужен внешний публичный ingress, TLS termination и отдельная эксплуатация web endpoint. При этом long polling полностью покрывает требования по latency и надежности для такого класса нагрузки.

Самая неприятная инженерная проблема на этом уровне связана с offset в Telegram. У Telegram offset глобальный на bot token, поэтому несколько независимых poller-инстансов не могут безопасно читать один и тот же поток updates без внешней координации: один воркер может продвинуть offset раньше, чем другой обработает свой batch, и часть событий будет потеряна. Поэтому я сознательно не делал горизонтальное масштабирование через несколько независимых long-polling consumers. Вместо этого у меня один ingress reader получает updates, а дальше внутри poller-а уже есть controlled concurrency: updates раскладываются по worker queue, но offset подтверждается только после подтвержденной downstream-доставки.

Ключевой момент в том, что offset не сохраняется сразу после получения update. Внутри poller-а есть contiguous ack tracking по локальным sequence number. Каждый update получает sequence, worker публикует его в Kafka, и только когда завершилась непрерывная последовательность подтвержденных сообщений, offset сохраняется в файл. Это защищает от типичной проблемы out-of-order completion: если более поздний update был опубликован быстрее более раннего, offset все равно не будет продвинут с дыркой. То есть модель такая: concurrent processing внутри, но commit семантика остается monotonic и contiguous.

Хранение offset сделано в файле на volume, а не в Redis или PostgreSQL. Причина прагматическая: offset poller-а относится к транспортному ingress и не является частью доменной модели. Для него не нужен distributed transaction coordinator. Нужна атомарная и достаточно надежная локальная персистентность. В Docker Compose это закрывается отдельным volume. Если бы система разворачивалась в нескольких availability zones и poller нужно было бы перемещать между нодами без локального state, тогда уже имело бы смысл вынести offset store во внешний highly-available storage.

Для устойчивости poller использует retry/backoff к Telegram API, bounded queues для ограничения in-flight нагрузки и graceful shutdown с дренированием очередей. Это важно: нельзя просто убить процесс, потому что тогда между «прочитал из Telegram» и «успел опубликовать в Kafka» появляется зона потери данных.

# Слайд 4. Orchestrator

Orchestrator является центром управления, но не центром доменной логики. Его задача не считать blackjack, а связывать транспортный мир и доменный мир. Он читает envelopes из Kafka, нормализует вход в команду, выполняет cheap local validation, вызывает game service, обновляет session context и рендерит ответ в Telegram.

Здесь Redis играет принципиально важную роль. Во-первых, это dedup layer по update_id, чтобы повторно пришедшие или повторно обработанные сообщения не приводили к повторному действию. Во-вторых, Redis хранит session context: turn_version, current player, available moves, последний bot message id и другие ephemeral данные, которые нужны для быстрого local guard и UX-поведения. В-третьих, Redis используется как таймерный backend. Таймеры не хранятся в памяти процесса, потому что память процесса умирает вместе с инстансом, а таймер хода должен переживать restart orchestrator-а.

На этом уровне я осознанно добавил локальные guard-проверки до вызова game service. Orchestrator умеет определить stale turn, «не твой ход» и «действие сейчас недоступно» на основании session context. Это уменьшает количество лишних round-trip к game service и улучшает UX: пользователь получает быстрый и понятный ответ, а не generic backend error. Но важный архитектурный момент в том, что эти guards не являются единственным источником истины. Каноническая валидация все равно остается в game service. То есть orchestrator делает fail-fast, а game service обеспечивает final correctness.

# Слайд 5. Надежность orchestrator

Основной класс проблем здесь связан не с happy path, а с гонками между действиями игрока, обработкой дублей и timeout events. Поэтому надежность orchestrator строится вокруг трех инвариантов.

Первый инвариант: один пользовательский update должен приводить максимум к одному доменному эффекту. Для этого используется дедупликация по update_id и идемпотентная модель обработки на уровне pipeline.

Второй инвариант: timeout нельзя применять к уже продвинувшемуся ходу. Для этого в протоколе есть turn_version. Любое player action и любой timeout привязываются к конкретной версии хода. Как только текущий игрок успешно сделал действие, старый timeout отменяется. Если timeout все же доехал позже и относится к устаревшей версии, он превращается в silent no-op без ложного уведомления в Telegram.

Третий инвариант: пользователь не должен терять актуальное сообщение состояния из-за невалидного действия. Поэтому cleanup старого bot message выполняется только после успешного действия текущего игрока. Если пользователь нажал не ту кнопку, отправил stale callback или возникла transport error при вызове game service, актуальное сообщение состояния остается на месте.

Отдельно отмечу таймерную механику. RedisTimerWorker хранит payload, индекс due tasks, claim key и done key. Это простая, но надежная claim-execute-mark-done модель. Она позволяет нескольким воркерам безопасно конкурировать за выполнение due timer без двойного исполнения. Если во время исполнения произошла ошибка, задача не теряется: она будет переопубликована в индекс на повторную попытку.

# Слайд 6. Game service

Game service реализован как отдельный HTTP JSON API с четко выделенной доменной логикой, persistence layer и state machine. Это ключевой сервис системы, потому что именно здесь живут правила blackjack, жизненный цикл игровой сессии, расчет дилера, settlement, обновление банков игроков и аудит переходов.

Почему не хранить игровую логику в orchestrator? Потому что orchestrator по своей природе зависит от Telegram transport semantics: callback payload, reply keyboards, message cleanup, dedup и таймеров. Если туда же поместить domain core, то любая смена transport behavior начнет рисковать доменной корректностью. Я разделил эти слои жестко: orchestrator оперирует командами и snapshot-ами, а game service принимает решения и транзакционно фиксирует side effects.

Внутри game service доменные правила отделены от persistence. Есть слой validators и turn rules, есть event context builder, есть dispatcher действий, dealer policy и settlement policy. Repository отвечает за загрузку контекста и транзакционную запись изменений. Такой разрез важен, потому что позволяет тестировать rules как pure domain behavior и отдельно тестировать корректность транзакционной записи и проекций snapshot-а.

В качестве базы данных выбран PostgreSQL. Здесь важна не просто персистентность, а транзакционность и возможность жестко зафиксировать инварианты на уровне схемы. Для игрового состояния это принципиально: изменение статуса сессии, перевод current position, списание ставки, добавление state audit record и фиксация hand state должны быть атомарными. SQLite или purely in-memory storage для такого сценария были бы проще, но не показали бы зрелую модель конкурентной и консистентной записи.

# Слайд 7. State machine

Игровой цикл описан явной state machine: от ожидания игроков и раздачи до хода игроков, хода дилера, settlement и закрытия сессии. Это решение выбрано потому, что у blackjack есть хорошо выраженные фазовые переходы и набор допустимых действий сильно зависит от текущего состояния. В таких условиях state machine лучше набора разрозненных if-else: она делает переходы явными, облегчает валидацию и помогает не размывать инварианты.

Практически это означает следующее. Действия hit, stand, double, split и insurance доступны только при соблюдении конкретных правил. Timeout трактуется как forced stand, но только если дедлайн реально истек и turn_version совпадает. После пользовательского действия сервис автоматически дренирует terminal phases: если игроки закончились, запускается ход дилера; если дилер закончил, запускается settlement; если settlement завершен, сессия закрывается. Снаружи это выглядит как одно действие, а внутри это каскад консистентных переходов.

Отдельно я разделяю runtime machine и persisted lifecycle. В БД у сессии есть бизнес-статусы вроде lobby_open, in_progress, stopped, closed. Это нужно потому, что жизненный цикл пользовательской сессии шире, чем чисто игровой фазовый автомат раунда.

# Слайд 8. Доменная модель и данные

С точки зрения данных модель строилась вокруг chat context как естественной единицы консистентности. Сущность Deck фактически привязана к chat_id, а поверх нее создаются игровые сессии. Это позволяет естественно реализовать важный инвариант: в одном чате не должно быть нескольких конкурирующих активных игровых контекстов. В PostgreSQL это дополнительно закреплено уникальными ограничениями и индексами, в том числе частичным уникальным индексом на активную сессию для конкретного deck.

Базовые сущности такие. Player хранит идентичность пользователя, bank и административные атрибуты вроде бана. Deck отражает контекст стола внутри чата. GameSession хранит lifecycle и runtime поля: статус, карты дилера, current position, current timer. PlayerToSession моделирует участие игрока в конкретной сессии: позицию, ставку и связанную руку. State является immutable audit log значимых переходов. Позже для split была добавлена отдельная таблица player_hands с ограничением уникальности по player_to_session_id и hand_index. Это важный эволюционный момент: split не пытались «впихнуть» в старую колонку cards, а вынесли в нормализованную модель, где каждая рука стала отдельным объектом с собственным статусом.

Почему это важно. Как только появляется split, состояние игрока становится многоруким, и попытка хранить все в одной записи быстро ломает и валидацию, и settlement, и UX. Отдельная таблица hands позволила сохранить доменную чистоту: для каждой руки отдельно известны карты, ставка, статус, а aggregate результат игрока считается поверх hand-level settlement. Это уже production-grade подход, а не ad hoc патч.

# Слайд 9. Масштабируемость, сложные инженерные проблемы и практики

Если говорить про масштабирование, то система разделяется на stateless и stateful компоненты. Poller и orchestrator по вычислительной логике в целом stateless, но работают поверх внешнего состояния: poller опирается на persisted offset, orchestrator на Redis и Kafka. Game service с точки зрения compute тоже можно горизонтально масштабировать, потому что каноническое состояние лежит в PostgreSQL. Stateful ядро здесь не процессы, а внешние хранилища и message broker.

Горизонтальное масштабирование orchestrator достигается consumer group моделью Kafka. Но чтобы это масштабирование не ломало порядок команд внутри одного чата, ключ Kafka сообщения формируется из chat context. Иными словами, partition key равен chat_id. Это означает, что все события одного чата гарантированно попадают в один partition и читаются последовательно одним consumer-instance в группе. Именно поэтому не возникает гонок между, например, callback на hit и timeout того же чата на уровне транспортного порядка.

Альтернатива, например partitioning по user_id, здесь хуже. В групповом раунде несколько игроков сидят в одном игровом контексте, и если разнести их события по разным partition, появится cross-partition race внутри одной сессии. Партиционирование по chat_id делает последовательность внутри стола линейной. Цена этого решения известна заранее: очень горячий чат становится hot partition и масштабируется только по одному воркеру. Но для данной предметной области это приемлемый и даже правильный компромисс, потому что внутри одного стола нам как раз и нужен последовательный порядок.

Отдельная сложная тема была с Telegram offset при нескольких воркерах. Как я уже сказал, несколько независимых poller-ов небезопасны из-за глобального offset. Поэтому масштабирование ingest реализовано как single ingress плюс internal fan-out. Внутри poller updates маршрутизируются по worker queue на основе стабильного source key, который приоритетно строится из chat_id. Это позволяет распараллелить downstream publishing и одновременно сохранить локальный порядок по chat context.

Еще один практический блок связан с выбором Kafka и развертыванием Redpanda. Я использовал Redpanda как Kafka-compatible broker, потому что для MVP и локального окружения он проще в эксплуатации, чем классическая Kafka-инсталляция. Не нужен отдельный ZooKeeper, меньше operational overhead, проще docker-compose bootstrap. При этом для кода это остается Kafka-модель: topic, key-based partitioning, consumer group, broker acks. Отдельным контейнером инициализируется topic, а сами сервисы стартуют только после готовности инфраструктуры. Это снижает количество гонок на старте и делает локальный стенд повторяемым.

С точки зрения инженерных практик я сознательно делал ставку на проверяемость инвариантов. В проекте покрыты unit и integration сценарии по всем трем сервисам. Для poller тестируются partitioning, bounded queue, offset store и contiguous ack tracking. Для orchestrator тестируются normalizer, command routing, local validation, transport error semantics, message cleanup, Redis timer worker и timeout pipeline. Для game service тестируются state machine, repository semantics, settlement policy, split, insurance, timeout race cases и интеграционные потоки с PostgreSQL. То есть тестами покрыт не только happy path, но и именно те места, где в production обычно и появляются проблемы: гонки, stale events, неправильный lifecycle и двойное исполнение.

Процесс разработки тоже был инженерно управляемым. Я работал итеративно, короткими инкрементами, с явным backlog и декомпозицией по вертикальным срезам: сначала базовый end-to-end поток, затем надежность транспорта, затем таймеры, затем UX guards, затем расширения домена вроде split и insurance. Для MVP это критично: если с самого начала пытаться строить «идеальную финальную систему», проект либо не доезжает до рабочего состояния, либо перегружается инфраструктурной сложностью. Итеративный подход дал возможность рано получить рабочий сквозной сценарий и затем последовательно усиливать reliability и domain richness.

Отдельно скажу про работу с AI-агентом. Я не использовал его как источник архитектурных решений по умолчанию. Я задавал ему жесткий контекст и ограничения через явные правила: маленькие инкременты, сначала план, затем реализация, обязательные тесты и обновление документации, без крупных несогласованных рефакторингов. По сути агент использовался как ускоритель инженерного цикла, а не как автономный архитектор. Лучше всего он ускорял шаблонный код, синхронизацию контрактов между слоями, генерацию тестовых каркасов и документирование уже принятых решений. Хуже всего он работал в местах, где требовалось понять concurrency semantics, инварианты state machine или компромиссы партиционирования. Эти решения я валидировал и проектировал вручную, потому что здесь цена красивой, но неверной генерации слишком высока.

Если говорить о best practices, которые я сознательно закладывал, то это прежде всего идемпотентность обработчиков, fail-safe error handling, retry механизмы на нестабильных участках, observability через сервисные логи и healthcheck-и, а также graceful degradation. Например, transport failure до game service не должен ломать session context. Stale timeout не должен шуметь пользователю. Ошибочный action не должен уничтожать актуальное состояние чата. Это небольшие детали, но именно из них и складывается production-quality UX.

# Слайд 10. Демо и вывод

Если коротко подвести итог, то для меня этот проект не про карточную механику как таковую, а про проектирование корректной event-driven системы вокруг внешнего нестабильного API и конкурентного игрового состояния. Здесь были важны не только функциональные команды, но и зрелые инженерные решения: четкие границы сервисов, правильный выбор точки асинхронности, транзакционная доменная модель, безопасная работа с offset, партиционирование по chat_id, таймеры без ложных срабатываний, дедупликация, тестирование race-сценариев и управляемый процесс разработки.

Именно поэтому я считаю, что система уже выглядит как production-grade заготовка, а не как учебный прототип. Она контейнеризована, разворачивается через Compose вместе со всей инфраструктурой, выдерживает restart-сценарии, сохраняет консистентность доменного состояния и уже сейчас спроектирована так, чтобы ее можно было масштабировать по active chats, а не переписывать с нуля при первом росте нагрузки.

В демо я покажу самый короткий пользовательский сценарий: запуск бота, команда /single_start, затем несколько игровых действий через кнопки. Но для меня ценность демо в том, что за этим простым сценарием стоит не просто handler на команду, а система, в которой порядок событий, таймеры и бизнес-инварианты уже контролируются на уровне архитектуры.
