# Слайд 1. Проект в 30 секунд

Это Telegram-бот для игры в Blackjack в двух режимах: single в личном чате и group в общем чате. На пользовательском уровне это выглядит просто: создать сессию, присоединиться, начать раунд и делать ходы через команды или кнопки. Но как инженерная задача это распределенная система, где важно не только поддержать happy path, но и гарантировать корректный порядок событий, защиту от дублей, консистентность таймеров и целостность игрового состояния.

Поэтому я проектировал проект сразу не как монолитный бот вокруг Telegram API, а как event-driven backend с четкими сервисными границами.

# Слайд 2. Общая схема

Сквозной поток такой: Telegram API отдает update в poller через long polling, poller публикует его в Kafka, orchestrator читает поток, нормализует update в команду, вызывает game service по HTTP и затем отправляет ответ обратно в Telegram. Redis используется для dedup, session context и таймеров, а PostgreSQL хранит каноническое состояние игры.

Микросервисная архитектура выбрана здесь по практической причине. В этой задаче транспорт, orchestration, таймеры и доменная логика развиваются с разной скоростью и имеют разные failure mode. Если смешать их в одном процессе, concurrency и error handling начинают протекать через весь код. Я разделил систему так: poller отвечает только за ingest updates, orchestrator за маршрутизацию, guards, таймеры и Telegram UX, game service за доменные правила и транзакционную запись состояния.

# Слайд 3. Poller и Telegram offset

Poller делает long polling к Telegram и публикует updates в Kafka. Я сознательно выбрал long polling, а не webhook, потому что для MVP это проще в эксплуатации: не нужен внешний ingress и отдельная настройка публичного endpoint.

Самая неприятная проблема здесь связана с offset Telegram. Offset глобален на bot token, поэтому несколько независимых poller-инстансов небезопасны: один инстанс может продвинуть offset, пока другой еще не обработал свои updates. Чтобы не терять события, у меня один ingress reader, а параллелизм реализован внутри poller-а.

Внутри сервиса update получает локальный sequence number, обрабатывается конкурентно, но offset сохраняется только по contiguous ack logic. То есть даже если более поздний update опубликовался раньше более раннего, commit не продвинется с дыркой. Это ключевой механизм, который делает concurrent ingest безопасным.

# Слайд 4. Kafka, Orchestrator и Redis

Граница между poller и orchestrator сделана асинхронной через Kafka. Это изолирует нестабильный внешний Telegram transport от внутренней бизнес-логики и дает возможность масштабировать обработку независимо от polling.

Ключевой момент для масштабирования: сообщения партиционируются по chat_id. Это означает, что все события одного чата попадают в один partition и читаются последовательно одним consumer-ом. Для игрового домена это критично, потому что игровой контекст существует на уровне стола, а не отдельного пользователя. Если бы partitioning был по user_id, в групповой игре появились бы cross-partition race condition внутри одной сессии.

Orchestrator при этом не считает blackjack. Он нормализует вход, выполняет cheap local guard-проверки, вызывает game service и управляет Telegram UX. Redis здесь нужен как fast state layer: там лежат dedup keys, session context с turn_version и available_moves, а также таймерные задачи.

# Слайд 5. Надежность и таймеры

Основные инварианты надежности такие. Первый: один update должен приводить максимум к одному доменному эффекту, поэтому используется дедупликация по update_id. Второй: timeout нельзя применять к уже устаревшему ходу, поэтому все действия и timeout-события привязаны к turn_version. Если ход уже сменился, старый timeout превращается в no-op. Третий: невалидное действие не должно ломать пользовательский UX, поэтому актуальное сообщение состояния не удаляется при ошибке.

Таймеры вынесены в Redis-backed worker. Задача хранит payload, due time, claim key и done key. Такая схема позволяет безопасно конкурировать за выполнение timeout-события и не исполнять его дважды. Если during execution возникает ошибка, задача не теряется, а уходит на повторную попытку.

# Слайд 6. Game service и доменная модель

Game service это отдельный HTTP API, где сосредоточена доменная модель blackjack. Именно он валидирует действия, ведет state machine раунда, выполняет ход дилера, считает settlement и транзакционно обновляет состояние игроков.

Почему логика вынесена отдельно от orchestrator. Потому что orchestrator зависит от Telegram-specific semantics: callback payload, message cleanup, reply keyboards, таймерный UX. Доменная модель не должна от этого зависеть. Поэтому orchestrator работает как application layer, а game service как canonical domain core.

В PostgreSQL хранятся основные сущности: Player, Deck, GameSession, PlayerToSession и State как audit log. Deck привязан к chat_id, что позволяет естественно поддерживать инвариант одной активной игровой сессии на чат. Когда появилась механика split, я не стал перегружать существующую запись игрока, а добавил отдельную таблицу player_hands. Это позволило сохранить чистую модель: каждая рука имеет собственные карты, ставку и статус, а aggregate settlement считается поверх hand-level состояния.

# Слайд 7. Технологический стек

Стек выбран не по принципу «популярно», а по соответствию задаче. Telegram Bot API дает внешний transport, long polling упрощает эксплуатацию. PostgreSQL нужен для транзакционной фиксации состояния и инвариантов на уровне схемы. Redis закрывает ephemeral state, dedup и таймеры, где важна скорость и короткое время жизни данных. Kafka, в моем случае Redpanda, решает задачу event streaming и consumer-group масштабирования без жесткой связности между ingest и orchestration. Docker Compose нужен для воспроизводимого окружения, где вся инфраструктура поднимается как единый стек.

Redpanda выбрана вместо классической Kafka из прагматических соображений: для локального и MVP-окружения она проще в эксплуатации, но при этом сохраняет Kafka-модель работы с topic, partition key и consumer group.

# Слайд 8. Масштабируемость и инженерные практики

С точки зрения масштабирования stateless-часть системы это poller и orchestrator, stateful-часть это PostgreSQL, Redis и broker. Orchestrator масштабируется горизонтально через consumer group. Game service тоже можно масштабировать горизонтально, потому что источник истины находится в базе данных. Ограничение возникает только там, где оно логически оправдано: один chat context должен обрабатываться последовательно.

Отдельно я закладывал production-oriented практики: идемпотентность обработчиков, fail-safe error handling, retry/backoff на нестабильных участках, healthcheck-и, сервисные логи и тестирование race-сценариев. В тестах покрыты не только happy path, но и timeout flow, stale events, local guards, split, settlement и транспортные ошибки.

Разработка шла итеративно, короткими инкрементами, с явным backlog. Это было важно для MVP: сначала получить рабочий end-to-end поток, а затем по слоям усиливать надежность и доменную сложность.

AI-агент я использовал как ускоритель, но не как источник окончательных решений. Он хорошо помогал в шаблонном коде, тестовых каркасах и документации, но решения по offset, concurrency, partitioning и state machine я валидировал вручную.

# Слайд 9. Вывод

Для меня ценность этого проекта в том, что это не просто Telegram-бот с набором команд, а корректно спроектированная event-driven система. Здесь важны не только игровые механики, но и зрелые backend-решения: четкие границы сервисов, безопасная работа с Telegram offset, partitioning по chat_id, транзакционная доменная модель, Redis-таймеры без ложных срабатываний, дедупликация и тестирование конкурентных сценариев.

Именно поэтому проект уже выглядит как production-grade заготовка: он контейнеризован, разворачивается вместе со всей инфраструктурой, сохраняет консистентность состояния и масштабируется по active chats без необходимости переписывать архитектуру при первом росте нагрузки.
