# Слайд 1. Проект в 30 секунд

Кратко о проекте: это Telegram-бот для игры в Blackjack в двух режимах - личная игра один на один и групповая игра в общем чате.

Как инженерная задача это не просто бот с командами, а распределенная система, где нужно гарантировать корректность не только в happy path, но и при гонках, дублях и сетевых сбоях.

Поэтому я изначально строил решение не как монолит вокруг Telegram API, а как backend с четкими сервисными границами и разделенной ответственностью.

# Слайд 2. Общая схема

Сквозной поток выглядит так: Telegram API отдает update в poller по long polling, poller публикует событие в Kafka, orchestrator читает топик, нормализует update в команду, вызывает game service по HTTP и отправляет ответ пользователю обратно в Telegram.

Redis используется для дедупликации, контекста сессий и таймеров, а PostgreSQL хранит каноническое состояние игры.

Почему именно микросервисное разделение. Потому что транспорт, оркестрация, таймеры и доменные правила развиваются с разной скоростью и имеют разные режимы отказа. Если смешать все в одном процессе, конкуренция и обработка ошибок начинают протекать через весь код.

В итоге роли такие: poller отвечает только за прием update, orchestrator за маршрутизацию, локальные guard-проверки, таймеры и Telegram UX, а game service за доменные правила и транзакционную фиксацию состояния.

# Слайд 3. Poller и Telegram offset

Poller делает long polling к Telegram и публикует updates в Kafka.

Самая сложная часть здесь связана с offset Telegram. Offset глобален на bot token, поэтому несколько независимых poller-инстансов небезопасны: один может продвинуть offset, пока другой еще не обработал свои события.

Чтобы не терять updates, я использую один ingress reader, а параллелизм реализую внутри poller.

Каждый update получает локальный sequence number, обрабатывается конкурентно, но offset продвигается только по подтвержденным sequence без дыр.

Даже если более поздний update опубликован раньше, commit не перескочит через необработанный более ранний. Это и делает конкурентный ingest безопасным.

# Слайд 4. Kafka, Orchestrator и Redis

Граница между poller и orchestrator сделана асинхронной через Kafka. Это изолирует нестабильный Telegram-транспорт от внутренней бизнес-логики и позволяет масштабировать обработку независимо от polling.

Критичный момент для корректности - partition key. События партиционируются по chat_id, поэтому все updates одного чата попадают в один partition и читаются последовательно одним consumer.

Для игрового домена это принципиально важно: игровой контекст живет на уровне стола, а не отдельного пользователя. Если партиционировать по user_id, в групповой игре появятся межпартиционные гонки внутри одной сессии.

Orchestrator при этом не считает Blackjack. Он нормализует вход, выполняет дешевые локальные guard-проверки, вызывает game service и управляет UX в Telegram.

Redis выступает как быстрый слой состояния: dedup-ключи, session context с turn_version и available_moves, плюс таймерные задачи.

# Слайд 5. Надежность и таймеры

Основные инварианты надежности такие.

Первый: один update должен приводить максимум к одному доменному эффекту. Для этого используется дедупликация по update_id.

Второй: timeout нельзя применять к устаревшему ходу. Поэтому действия и timeout-события привязаны к turn_version. Если ход уже сменился, старый timeout становится no-op.

Третий: невалидное действие не должно ломать UX. При ошибке текущее сообщение состояния не удаляется, чтобы пользователь не терял контекст партии.

Таймеры вынесены в отдельный worker на Redis. Задача хранит payload, due time, claim key и done key.

Такая схема позволяет безопасно конкурировать за выполнение timeout-события и не исполнять его дважды. Если во время выполнения возникает ошибка, задача не теряется, а уходит на повторную попытку.

# Слайд 6. Game service и доменная модель

Game service - это отдельный HTTP API, где сосредоточена доменная модель Blackjack.

Он валидирует действия, ведет state machine раунда, выполняет ход дилера, считает settlement и транзакционно обновляет состояние игроков.

Логика вынесена отдельно от orchestrator, потому что orchestrator зависит от Telegram-специфики: callback payload, очистка сообщений, клавиатуры и таймерный UX. Доменная модель не должна зависеть от этих деталей.

В PostgreSQL хранятся ключевые сущности: Player, Deck, GameSession, PlayerToSession и State как журнал состояния.

Deck привязан к chat_id, что естественно поддерживает инвариант: в одном чате одновременно активна только одна игровая сессия.

# Слайд 7. Технологический стек

Стек подбирался не по принципу популярности, а по соответствию задаче.

Telegram Bot API - внешний транспорт, long polling - простой и предсказуемый ingress.

PostgreSQL - транзакционная фиксация состояния и инварианты на уровне схемы.

Redis - быстрый слой для краткоживущего состояния: дедупликация, сессионный контекст и таймеры.

Kafka, в моем случае Redpanda, - поток событий и масштабирование через consumer group без жесткой связки между ingest и orchestration.

Docker Compose - воспроизводимое окружение, где весь стек поднимается одной командой.

Redpanda выбрана прагматично: для локальной разработки и MVP она проще в эксплуатации, но сохраняет совместимую Kafka-модель topic, partition key и consumer group.

# Слайд 8. Масштабируемость и инженерные практики

С точки зрения масштабирования stateless-часть системы - это poller, orchestrator и game service, stateful-часть - PostgreSQL, Redis и broker.

Orchestrator масштабируется горизонтально через consumer group. Game service также масштабируется горизонтально, потому что источник истины находится в базе данных.

Последовательность оставлена только там, где она логически необходима: один chat context должен обрабатываться по порядку.

Дополнительно я закладывал практики, ориентированные на production: идемпотентность обработчиков, отказоустойчивая обработка ошибок, retry/backoff на нестабильных участках, healthcheck, сервисные логи и тесты на race-сценарии.

Тесты покрывают не только happy path, но и timeout flow, stale events, локальные guard-проверки, split, settlement и транспортные ошибки.

# Слайд 9. Вывод

Итог такой: проект уже можно считать production-ориентированным минимальным жизнеспособным продуктом (MVP).

Он контейнеризован, поднимается вместе со всей инфраструктурой, сохраняет консистентность состояния и масштабируется по активным чатам без переписывания архитектуры при первом росте нагрузки.

Для меня ключевой результат не только в том, что бот играет в Blackjack, а в том, что система остается корректной в условиях конкуренции, повторов и сбоев внешних зависимостей.

Именно это я считаю главным инженерным достижением проекта.
