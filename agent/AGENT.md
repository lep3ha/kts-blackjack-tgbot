# AGENT.md

## Назначение
Цель: развивать учебный микросервисный проект Blackjack Telegram Bot последовательно, ревью-пригодно и без избыточной сложности.

## Контекст проекта
- Telegram Bot API
- PostgreSQL (состояние игры)
- Redis (таймеры, кэш, dedup)
- Poller (long polling)
- Game Service (доменная логика)
- Orchestrator (роутинг/guards/UX)
- Timer Worker (таймауты)
- Sender (отправка сообщений в Telegram)

## Приоритеты (в порядке важности)
1. Корректность бизнес-логики и инвариантов состояния.
2. Понятность и предсказуемость кода.
3. Малый и безопасный размер изменений.
4. Покрытие тестами и прозрачная проверка результата.
5. Обновление документации под внесенные изменения.

## Обязательный рабочий процесс

### 1) План перед реализацией
Для любой нетривиальной задачи агент обязан сначала дать короткий план:
- 3-7 шагов;
- ожидаемый результат каждого шага;
- перечень файлов, которые планируется менять.

### 2) Подтверждение от пользователя
Реализация начинается только после явного подтверждения плана пользователем.

### 3) Инкрементальная реализация
- Делать по одному логическому блоку за раз.
- После каждого блока: показать что изменено и зачем.
- Перед следующим блоком: запросить подтверждение.

## Ограничения на изменения
- Не делать крупный рефакторинг без прямого согласования.
- Не переименовывать файлы/папки без согласования.
- Если файл разрастается, сначала предложить декомпозицию и получить одобрение.
- Предпочитать минимальные диффы, не трогать несвязанные участки.

## Стандарты кода
Код должен:
- соответствовать задаче и текущей архитектуре;
- иметь ясные docstring там, где это нужно;
- использовать явные схемы запросов/ответов;
- использовать pydantic для моделей данных, где применимо;
- быть типизированным (typing + согласованные аннотации);
- оставаться читаемым и детерминированным по поведению.

## Тесты и валидация
После каждого утвержденного плана агент обязан:
- добавить/обновить тесты на измененный функционал;
- прогнать релевантные тесты затронутых сервисов;
- показать краткий итог прогонов (что запускалось и что прошло/упало);
- отдельно указать, что не удалось запустить, если есть ограничения окружения.

## Документация
При изменении контрактов, сценариев или архитектурных решений обновлять соответствующие документы в репозитории.

## Ограничение на сложность
- Не предлагать избыточные enterprise-решения.
- Это учебный проект: решения должны быть инженерно корректными, но прагматичными.

## Формат ответов агента
- Кратко и по делу.
- Для каждого изменения объяснять: что сделано, зачем, компромисс.
- Если есть варианты: давать 2-3 опции с плюсами/минусами и явной рекомендацией.

## Definition of Done (DoD)
Задача считается завершенной, когда:
1. План согласован и выполнен инкрементами.
2. Код внесен минимально необходимым объемом.
3. Тесты на изменения добавлены/обновлены и запущены.
4. Результаты проверки явно показаны.
5. Документация обновлена при необходимости.

## Шаблон мини-отчета после шага
1. Что изменено.
2. Какие файлы затронуты.
3. Какие тесты запущены и результат.
4. Что предлагается следующим шагом.
